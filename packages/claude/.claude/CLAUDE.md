# グローバル設定（全プロジェクト共通）

## 日本語の書き方（コミット・コメント・ドキュメント共通）

- 一文は途中で改行せず、句点の後で改行すること
- 一文は短く書き、文意は一つに絞ること
- 理由と結果は文を分けること（「〜のため、〜」で繋げない）
- 意味・論理のまとまりを分けたい時は空行を入れて段落を分けること
- 時制は日本語として自然なものを選ぶこと
- 英単語と日本語の間には半角スペースを入れること

## コードのコメント

- 見出し・セクション名など、ラベルとして置くものは英語で書くこと
- 「なぜそうしたか」「何のための設定か」の説明は日本語で書くこと
- 未来の自分が読んで分かる最小限に留め、冗長に書かないこと
- 説明は要点だけに絞り、調べた経緯や検討の過程はコミットメッセージへ回すこと
- 次の場面ではタグを付けること（todo-comments.nvim が色を付けて拾う）
  - TODO … 後でやること
  - NOTE … 前提や補足。読み飛ばすと誤解する情報
  - WARNING … 触ると壊れるもの、直感に反する挙動
  - HACK … 常套手段でない回避策。理由と、外せる条件を書く
  - FIXME … 既知の不具合。直っていないと分かるようにする

## commit 規約

勝手にコミットせず、コミット案を以下に準じて書いて提示すること。
コミットして、と指示がある時にコミットを行うこと。
コミット済みの履歴を書き換える（amend / rebase）時も、同じく指示を待つこと。ただし、提案があれば提示すること。

- コミットは論理のまとまりを単位とすること（アトミックコミット）
- それ単体でエラーなく意図した動作になり、revert しても壊れない粒度に保つこと
- コミットメッセージに `Co-Authored-By` などの署名・フッターを付けない
- コミットメッセージは Conventional Commits 形式：`type(scope): 件名`
  - type / scope は英語で書き、type は下記から選ぶこと
  - 件名と本文は日本語で書く（例：`feat(header): ナビゲーションを追加`）

- type（`git log --grep` で絞り込めるよう、意味で分ける）
  - feat … 利用者ができることが増えた場合（触ると何か起きる UI の追加も含む）
  - fix … 壊れていたものが直ったとき
  - ui … 見た目のみの変更（振る舞いは変わらない）
  - style … コードの整形
  - refactor … 利用者から見て何も変わらない内部の整理
  - docs … 開発者向けの文書（README、ノート）
  - chore … 上のどれでもない（誤字修正、設定、依存、雑務）

- scope（`git log --grep` で引ける単位にする）
  - 変更の主眼になったもののみを書くこと（複数ファイルに跨る時も主眼一つに絞る）
  - 同種の変更が既に使っている scope を優先すること。新しい名前は既存のどれにも収まらない時だけ作る
  - 1 件で終わりそうな名前は scope にせず、件名に書くこと
  - 表記は固定すること（小文字、単数形と複数形を混ぜない）
  - 機能や領域の名前を書くこと。ディレクトリ構成がそれを表しているなら親ディレクトリ名を使う
  - ルート直下のものは拡張子を除いたファイル名あるいはその短縮名とすること

- 件名
  - 体言止めで簡潔に要点を書くこと
  - 体言止めが不自然な時は辞書形（〜する）で書くこと（過去形は使わない）
  - 50 桁程度に収めること。収まらない時はコミットの分割を検討する

- 本文
  - コードからは読み取れない「なぜ」を中心に書くこと
  - 変更前に何が問題として起きていたか、なぜその方針を選んだかを残すこと
