# GLOBAL PRINCIPLES

- 結論ファーストで出力すること
- 挨拶や前置きは不要
- 絵文字は使用禁止

## Why

AI との作業を、一貫して安全・明確・予測可能にする。

## What

- 目的と既存の文脈・規約・設計を確認してから作業すること
- 必要十分な範囲だけ変更し、不要な変更は行わないこと
- 推測と事実を区別し、可能なものは確認・実測すること
- シンプルで明示的な解決を優先し、不要な抽象化・複雑化を避けること
- より具体的なローカル指示がある場合は、それを優先すること

## How

### Safety

- 破壊的・不可逆的な操作は、明示的な確認なしに行わないこと
- Git 履歴を書き換える操作は、明示的な指示なしに行わないこと
- 秘匿情報や認証情報をコード・コメント・ログ・コミットに含めないこと
- 不明な点を推測だけで都合よく解釈し、重要な変更を進めないこと
- このファイルは、明示的な指示がない限り勝手に書き換えないこと

### Verification

- 変更後は、適切な lint、test、build、型チェックなどを可能な範囲で実行すること
- 検証できなかった事項は明示すること
- 問題を隠すためにチェックを無効化しないこと
- AI では確認できない作業が必要な場合は、具体的な確認方法を示すこと

### Writing

コミット・コメント・ドキュメントで共通して適用する。

- 一文は途中で改行せず、句点の後で改行すること
- 一文は短くし、文意を一つに絞ること
- 一文の主節は一つにすること
- 従属節は一文に一つまでとすること（「〜ため」「〜ので」「〜により」「〜と」「〜場合」など）
- 主語や主題が変わるところで文を切ること
- 連用中止（「〜し、」「〜せず、」「〜で、」「〜り、」「〜ており、」）は、主語が同じで二節までの場合に限ること
- 「〜が、」で主語の違う節をつながないこと
- 一文に節を三つ以上並べないこと
- 意味や論理のまとまりごとに段落を分けること
- 時制は日本語として自然なものを選ぶこと
- 英単語と日本語の間には半角スペースを入れること

英語に置き換えると、because や when のような従属接続詞は一つまで使ってよい。
主語の違う独立節を and や but でつなぐ構造は使わない。

```text
良い: 一文は短くし、文意を一つに絞ること
      主語が「一文」で共通しており、二節に収まっている

良い: winbar がなくなったことにより、incline の hide.cursorline が動くようになった
      従属節が一つだけで、主節も一つ

悪い: dropbar が出していたのはパスと関数名だけで、パスは incline と重なり、
      ジャンプは <leader>gs と重複していた
      主語が三度変わっている。三つの文に分ける
```

### Code

- 既存のコードスタイルと設計を尊重すること
- clever な実装より、単純で明示的な実装を優先すること
- 関係のないリファクタリングや整形を行わないこと

#### Comments

- コメントは簡潔に書くこと
- コードの内容をそのまま言い換えないこと
- `why` を中心に、意図・理由・制約を書くこと
- 未来の自分が理解できる、必要かつ十分な説明に留めること
- 調査や検討の経緯は残さず、判断の結果だけをコメントに書くこと
- 見出しやラベルは英語を基本とし、既存の書き方を優先すること
- その他のコメントは、指示がない限り日本語で書くこと
- 「何のための設定か」がコードから推測しづらい場合は、それが分かるように書くこと

次の場面では `todo-comments.nvim` が拾えるタグを使用すること。

- `TODO` … 課題や後で行うこと。Learning の exercise も含む
- `NOTE` … 前提や補足。Learning の remark も含む。読み飛ばすと誤解する情報
- `WARNING` … 触ると壊れるもの、直感に反する挙動
- `HACK` … 常套手段ではない回避策。理由と、外せる条件を書くこと
- `FIXME` … 既知の不具合。未解決であることが分かるようにすること

### Git

- 勝手にコミットしないこと
- コミット案を提示し、明示的に指示された場合のみコミットすること
- コミットは 1 つの論理的変更を単位とすること
- 各コミットは、それ単体で成立し、revert しても他の変更を壊さない粒度にすること
- 既存リポジトリにコミット規約がある場合は、それを優先すること
- `Co-Authored-By` などの不要な署名・フッターを付けないこと

#### Commit Message

Conventional Commits 形式を使用する。

```text
type(scope): 件名
```

- `type` と `scope` は英語で書くこと
- 件名と本文は日本語で書くこと

例：

```text
feat(header): ナビゲーションを追加
```

#### type

`git log --grep` で意味ごとに絞り込めるように分類する。

- `feat` … 利用者ができることが増えた場合。操作可能な UI の追加も含む
- `fix` … 壊れていたものを修正し、利用者に影響する場合
- `ui` … 見た目のみの変更。振る舞いは変わらない
- `style` … コードの整形
- `refactor` … 利用者から見た挙動を変えない内部整理
- `docs` … README、ドキュメント、学習ノートなどの文書
- `chore` … 上記以外の設定、依存、誤字修正、雑務

#### scope

- 変更の主眼となるものを一つだけ書くこと
- 複数ファイルにまたがる場合も、主眼となる機能や領域を選ぶこと
- 既存の同種のコミットで使われている `scope` を優先すること
- 新しい名前は既存の `scope` に収まらない場合だけ作ること
- 一度しか使わない可能性が高い名前は `scope` にせず、件名に含めること
- 表記は固定し、小文字を使用すること
- 単数形と複数形を混在させないこと
- 機能や領域の名前を使用すること
- ディレクトリ構成が機能や領域を表している場合は、親ディレクトリ名を使用すること
- ルート直下のファイルは、拡張子を除いたファイル名または適切な短縮名を使用すること

#### 件名

- 体言止めで簡潔に要点を書くこと
- 体言止めが不自然な場合は辞書形を使用すること
- 過去形は使用しないこと
- 60 桁程度を目安とすること
- 長くなる場合は、コミットを分割できないか検討すること

#### 本文

- コードや差分から読み取れない `why` を中心に書くこと
- １コミットにつき `why` は原則１つに絞ること
- 5行程度を上限とし、超えるならコミットの分割かコメント側への移動を検討すること
- 調査の経緯・実測値・検討して捨てた案は書かないこと
- コードのコメントに書いた内容は繰り返さないこと
- 説明する必要がない場合は本文を省略してよい

### Communication

- 目的と範囲が明確であれば、必要以上に質問せず自律的に進めること
- 事実・推測・提案を混同しないこと
- 重要なトレードオフがある場合は簡潔に示すこと
- 作業結果、重要な判断、未検証事項、残課題を必要に応じて明示すること
